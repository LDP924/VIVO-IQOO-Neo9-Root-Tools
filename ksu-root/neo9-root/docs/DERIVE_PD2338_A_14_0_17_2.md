## 4. 旁证：两版内核 config 对比

内核内嵌 IKCONFIG（`IKCFG_ST` 在文件偏移 `0x18644a0`）。解出 5.15.137 的精确 config，
与 15.1.14.7 的 `/proc/config.gz`（=`~/kernel/vivo-neo9-android15/.config`）对比：
两版**共 471 项**设置不同（多为厂商驱动模块：charger/camera/fingerprint/BBK_* 等），
但**决定上述结构体布局的开关完全一致**：

```
CONFIG_LOCKDEP=n  DEBUG_LOCK_ALLOC=n  PROVE_LOCKING=n  DEBUG_RWSEMS=n  DEBUG_MUTEXES=n
CONFIG_KEYS=y     SECURITY=y  SECURITY_SELINUX=y     DEBUG_CREDENTIALS=n
CONFIG_THREAD_INFO_IN_TASK=y   PGTABLE_LEVELS=3   ARM64_VA_BITS=39
CONFIG_ARM64_MTE=y  KASAN_HW_TAGS=y  STACKPROTECTOR_PER_TASK=y
```

这与第 3 节"24 个字段偏移逐一吻合"互为印证 —— 两版是同一套 vivo GKI 配置体系，
只是编译器（clang 14 → 18）与厂商驱动集不同。

## 9. init-hook 载荷常量（2026-09-27 补做）

init-hook 的载荷偏移取自固件里的 `/system/bin/init`（**不在 boot.img 里**，所以要单独拿
`system.img`）。本节的输入是 `PD2338C_A_14.0.17.2.W10.V000L1/system.img`，6,249,398,272 B，
sha256 `87c6651c8c2762c85c1d4e3f4a7def9c7e4b4c494a35f7a44a3cd34712372b61`。

### 9.1 取 init（EROFS 只抽一个文件）

`system.img` 是 **EROFS**（魔数 `0xe0f5e1e2` @1024），6.2 GB，解包后 8.7 GB。沙箱里
`erofsfuse` 挂载被禁（`fusermount: Operation not permitted`），所以：

```sh
fsck.erofs --extract=<工作区目录> --no-preserve system.img   # 55 秒，8.2 GB
cp <工作区>/system/bin/init ./init
```

> `neo9-root/tools/erofs_extract_one.py` 本想"只解一个文件"（按 extent 逐块 LZ4），
> 但本镜像是 **compact/interlaced** 格式（一个 extent 的 out_len 可 > 4096 物理字节），
> 逐 extent 独立解压在中间某个 extent 上就会失败并明确报错 —— 该工具保留作诊断/备用，
> **当前固件请用 `fsck.erofs --extract=`**。

| 项 | 值 |
|---|---|
| 路径 | `/system/bin/init` |
| 大小 | 2,969,024 B（与 erofs inode 的 Size 一致） |
| sha256 | `b3f8d7ca4492110b54093e2182a0e603…` |
| 类型 | ELF64 AArch64 **PIE**，动态链接，解释器 `/system/bin/bootstrap/linker64` |
| BuildID | `50cc181acc9fe6297e915f317f9f1bc0` |

### 9.2 关键语义（先确认，再推值）

`run_init_hook_lpe()` 用 `mm->start_code` 做基准：
`patch_va = start_code + (PATCH_FILE_VA - TEXT_FILE_VA)`。
内核源码 `fs/binfmt_elf.c`（本机 `~/kernel/vivo-neo9-android15`，同 5.15 stable）写得很清楚：

```c
k = elf_ppnt->p_vaddr;
if ((elf_ppnt->p_flags & PF_X) && k < start_code)  start_code = k;   /* PF_X 段的**最小** p_vaddr */
...
k = elf_ppnt->p_vaddr + elf_ppnt->p_filesz;
if ((elf_ppnt->p_flags & PF_X) && end_code < k)    end_code = k;     /* PF_X 段的**最大** 结束地址 */
...
start_code += load_bias;  end_code += load_bias;
mm->end_code = end_code;  mm->start_code = start_code;
```

⇒ **`INIT_TEXT_FILE_VA` = 可执行 LOAD 段的 `p_vaddr`**（本 init 只有一个 PF_X 段）。

### 9.3 推导结果（`tools/init_hook_derive.py`）

本 init 的段布局：`LOAD 0xe2000/0x1dca88 R E` → 可执行范围 `[0xe2000, 0x2bea88)`。

| 常量 | 值 | 依据 |
|---|---|---|
| `INIT_TEXT_FILE_VA` | `0xe2000` | PF_X LOAD 的 p_vaddr（§9.2） |
| `INIT_HOOK_PATCH_FILE_VA` | `0x2bd3a8` | `.rela.plt` 第 350 项（`r_offset 0x2c4630`，符号 `__system_property_update`）对应的 PLT 桩 |
| `INIT_HOOK_PATCH_EXPECT0..3` | `f0000030 f9431a11 9118c210 d61f0220` | 该桩的原始 4 条指令：`adrp x16` / `ldr x17,[x16,#0x630]` / `add x16,x16,#0x630` / `br x17` |
| `INIT_HOOK_CAVE_FILE_VA` | `0x2bea88` | 可执行段尾的映射填充（见下） |
| `INIT_HOOK_CAVE_EXPECT0` | `0` | 该区全 0（实测 1400 B 全 0） |

**代码洞为什么取段尾**：内核 `elf_map` 把 mapping 长度**向上取整到页**，所以
`[0x2bea88, 0x2bf000)` 这段虽超出 `p_filesz`，仍在可执行映射内、且读到的是**文件里
那 1400 字节**（链接器留的 0）。它天然满足运行期的三条约束：≥244 B、整段落在同一页
（页内偏移 `0xa88`，`0xa88+244 < 0x1000`）、可执行。15.1.14.7 用的也是同类填充。

**自检（工具会打印，任一条不满足即退出）**：
- 补丁点落在 `[TEXT_FILE_VA, TEXT_FILE_VA+p_filesz)` 内 ✓
- 桩的 GOT 目标（`adrp`+`ldr` 算出的 `0x2c4630`）与 `.rela.plt` 里
  `__system_property_update` 的 `r_offset` 完全一致 ✓（不是"看着像 PLT 桩"）
- 代码洞 244 B 全 0 且同一页 ✓

**交叉验证**：15.1.14.7 的旧值 `INIT_HOOK_PATCH_EXPECT3 = 0xd61f0220`（`br x17`）
与新值**逐字相同**，前三条也都是同形态的 `adrp/ldr/add`（只是立即数不同）——
说明两次推的是同一类目标（`__system_property_update` 的 PLT 桩）。

复现：
```sh
P=neo9-root/tools/init_hook_derive.py
python3 $P init --symbol __system_property_update
```

### 9.4 ⚠️ 重要：这条路**没有接线**，所以产物二进制没变

`run_init_hook_lpe()` 在源码里**没有任何调用点**（`dirtypt_ro_setup` 也只被它调用）。
因为它是 `static` 且不可达，编译器把整个函数删掉，所以：

- 补齐 init-hook 常量后重编，**二进制逐字节不变**（14.0.17.2 产物 md5 仍
  `f5d2fe452b87da41fd2cd3b32ab1019d`）——这不是"没生效"，是"根本没被编进去"
- 本次改动的价值在于：① 常量与断言齐备（`_Static_assert` 已把它们钉住，将来漂移会编不过）
  ② 去掉了此前"本 profile 显式拒绝 init-hook"的人为限制 ③ 工具与流程可复现
- **要真能用**，还需接线：选模式的开关（默认关）、目标 PID 的选取、与 vr.ko / vhangup
  路径的先后顺序、失败回滚策略。写入对象是 **PID 1 的代码页**，风险面明显大于
  vhangup stub，属于需要单独设计 + 真机验证的一步。
