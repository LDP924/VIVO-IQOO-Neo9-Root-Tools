## 11:00 重构：四个 Activity → 单 Activity + 跟手分页

**用户要求**：切页要"跟手左右滑"（上一版只做了转场动画，手指拖动做不到）。
这不是加动画能解决的 —— 四个独立 Activity 无法跟手，必须合并成单 Activity + 分页容器。

### 架构

| 前 | 后 |
|---|---|
| `MainActivity` / `LogActivity` / `SettingsActivity` / `AboutActivity` 四个 Activity | `PagerActivity` 一个入口 + `ui/page/` 下四个 `Page` 子类 |
| `activity_main/log/settings/about.xml` | `page_home/log/settings/about.xml` + `activity_pager.xml` |
| `Dock` 跳 Activity + 转场动画 | `Dock.attach/highlight` 切 `pager.setCurrentItem(i)` |
| `Insets.apply(activity, topBar, bottom)` | `Insets.apply(activity, topBars: List<View>, bottom)`（四页各有顶栏） |

新建 `ui/SwipePager.kt`（`HorizontalScrollView` 子类）：`onMeasure` 把每个页面拉成与容器等宽；
`ACTION_UP` 自己 snap（先看甩动速度 ≥ `scaledMinimumFlingVelocity`，否则看位移是否过半），
**不把 UP 交回父类** —— 否则 ScrollView 会再触发一次 fling 滚到两页之间。

### 两个必须一起改的点

1. **`InnerScrollView` 原先无条件锁父容器** → 会吃掉水平手势，在日志/输出区上就滑不动页。
   改成只在 `|dy| > |dx|`（垂直意图明确）时才锁。
2. **四个页面有同名 id**（`topBar` / `tvLog` / `btnCopyLog` …）→ 页面类所有 findViewById 都走
   自己的 `root`（`Page.id()`），否则会串页。layout 里重复声明同一 id 本身是合法的。

另：换主题色板会 `recreate()` 整个容器 → 用 `savedInstanceState` 记住当前页序号，重建后停在原页。

### 头号结论：这条路**没有接线**，所以补齐常量后**产物二进制一字未变**

`run_init_hook_lpe()` 在源码里**没有任何调用点**（`dirtypt_ro_setup()` 也只被它调用）——
2026-08 探索 init-hook 路线时留下的实现，后来主线改走 vhangup stub + 内置 su。
因为它是 `static` 且不可达 → 编译器整段删除 → 常量改 0 → 真值，**重编后 md5 仍是
`f5d2fe452b87da41fd2cd3b32ab1019d`**。这不是"没生效"，是"根本没被编进去"。
（这同时验证了"改常量不影响可达行为"的说法。）要真能用，还得接线（默认关的开关 +

### 取 init（EROFS 里只拿一个文件）

`system.img` 6.25GB（sha256 `87c6651c…`），EROFS（魔数 @1024），解包后 8.7GB。
- **`erofsfuse` 挂载被沙箱禁**（`fusermount: Operation not permitted`，虽然 /dev/fuse 在）
- 我写的"按 extent 逐块 LZ4"只抽一个文件的工具**在本镜像上不成立**：它是
  **compact/interlaced** 格式（一个 extent 的 out_len 可 >4096 物理字节，块间有依赖），
  解到中间某个 extent 就失败（工具会明确报错而不是产出错文件）→ 保留作诊断用
- 实际可行：`fsck.erofs --extract=<工作区> --no-preserve system.img`，**55 秒 8.2GB**

### 新常量（`tools/init_hook_derive.py`）

先定语义（读本机内核源码 `fs/binfmt_elf.c`，同 5.15 stable）：
`start_code` = **PF_X 段里最小的 p_vaddr**，`end_code` = **PF_X 段里最大的 p_vaddr+p_filesz**
（都加 load_bias）⇒ `INIT_TEXT_FILE_VA` 就取可执行 LOAD 的 p_vaddr。

| 常量 | 14.0.17.2 | 15.1.14.7（旧） |
|---|---|---|
| `INIT_TEXT_FILE_VA` | `0xe2000` | `0x721000` |
| `INIT_HOOK_PATCH_FILE_VA` | `0x2bd3a8`（`__system_property_update` 的 PLT 桩） | `0x995cd8` |
| `EXPECT0..3` | `f0000030 f9431a11 9118c210 d61f0220` | `90000050 f9437e11 911be210 d61f0220` |
| `INIT_HOOK_CAVE_FILE_VA` | `0x2bea88`（可执行段尾的映射填充，1400 B 全 0） | `0x997808` |

交叉验证：两版 `EXPECT3` 都是 `0xd61f0220`（`br x17`），前三条都是同形态 `adrp/ldr/add` —— 
推的是同一类目标。**代码洞为什么取段尾**：内核 `elf_map` 把长度向上取整到页，
`[p_filesz 结尾, 页尾)` 这段仍在可执行映射内、读到的是文件里的 0（链接器留的），
天然满足"≥244B + 同一页 + 可执行"三条运行期约束。工具自检里最硬的一条是
**"桩算出的 GOT 目标 == 该符号在 .rela.plt 的 r_offset"**（不是"看着像 PLT 桩"）。
