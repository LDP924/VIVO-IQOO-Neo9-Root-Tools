### CVE-2026-31629（NFC LLCP missing return UAF）核验（00:1x）

- 档案：nfc_llcp_recv_hdlc/nfc_llcp_recv_disc 在 LLCP_CLOSED 分支缺 return →
  双 release_sock + 双 nfc_llcp_sock_put → 引用计数下溢 UAF。AV:A（NFC 近场），
  无公开 exploit。修复于 6.6.136/6.12.83/6.19.14/7.0.1；linus 7.1-rc1 (2b5dd4632)。
- 16.2.13.2 (5.15.197) 判定：**不存在（已修）**。NFC LLCP 内建在内核
  （kallsyms 全套 nfc_llcp_* 在 kernel.elf），反汇编核验两函数：
  - recv_disc@0x…f2ec：CLOSED 分支(cmp #4)→ release_sock(+0x94)→ 内联 sock_put
    (+0x218 块)→ 成功路径汇入 +0x358 尾声 → ret；主路径(+0x13c 起，含第二处
    release_sock+0x19c)与 CLOSED 分支**互斥**，无穿透。

    → b.gt → +0x4C8 尾声 ret；第二处 release_sock(+0x2c4)在互斥主路径。

### stage0 设计定型（01:5x）—— 关键机制 + 本内核常量

- **机制（上游 zt_stage0 的实质）**：freed k_itimer 仍在 victim timer rbtree 里，内核
  `rb_erase` 在"无左子"路径退化为两次确定写：
  `mem[forged_parent+8]=forged_child`（把 forged_child 写进 **random_table[4].data**，
  即 /proc/sys/kernel/random/boot_id 的数据指针）与 `mem[forged_child]=forged_parent`
  （写进泄漏源的第一 qword）。读回 boot_id（**mode 0444，shell 可读**）⇒ `q0==forged_parent`
  自证落地，`q1` 是自指 list_head 的 prev（镜像映射下的滑动指针）⇒ `slide = q1 - 链接期地址`。
- **为什么首次落点不需要 slide**：**用直接映射（linear map）别名**。arm64 镜像映射随 KASLR 滑，
  线性映射基址固定（VA_BITS=39 → PAGE_OFFSET=0xffffff8000000000），同一物理页两个 VA。
  这就是上游 `direct_bootid_parent`/`direct_cycle_c` 命名的由来。
- **本内核常量（已核对）**：`random_table`=0xffffffc00af27058（stride 0x40），
  `random_table[4].data` 字段@0xffffffc00af27160（内容 0xffffffc00b19dd59=sysctl_bootid ✓）；
  **forged_parent=0xffffffc00af27158**、**forged_child=0xffffffc00adadd28**
  （= `blacklisted_initcalls`，自指 list_head，boot 后不再遍历 ⇒ 改它相对安全；
  备选 vsock_tap_all / vm_list；扫描到 1709 个自指候选）；
  delta(stext_VA-PA)=0xffffffbf60000000 ⇒ **linear 别名** forged_parent=0xffffff80aaf27158、
  forged_child=0xffffff80aadadd28。
- **回收手法**：socket 发送队列（SOCK_STREAM + 定长 send + 伪造 timer 模式按 0x108 步长重复 31 份、
  首份 +0x78）——free/reclaim 必须同 CPU、收尾前不 recv。本内核两个干扰：
  **SLUB_MIRROR**（影响跨 cache 布局，需实测定参）、**INIT_ON_ALLOC = 全零**（不能依赖"新分配带旧内容"，
  必须走"分配后我们写入"的路径，socket send 满足）。载荷页 order 需实测标定。
- **判据（无需 root）**：`cat /proc/sys/kernel/random/boot_id` → STAGE0_PASS/MISS；
  顺带回答"设备是否真的无 KASLR"（项目笔记 14.x 记"无 KASLR"，本 stage 会证实）。
- 文档：`neo9-root/cve64560/stage0_design.md`（含全部常量、风险与回退）。
- 设备侧探针结论：`/proc/kallsyms`、`/proc/sys/kernel/kptr_restrict`、`/proc/iomem` 对 shell
  **全部 Permission denied** ⇒ 拿不到免费 slide。

### 64560 stage0 实现与真机调试（02:0x）

- **机制从源码定案**（`kernel/time/posix-cpu-timers.c:470-530`）：
  `sighand = lock_task_sighand(p,&flags)`；`sighand == NULL` 的漏洞分支**跳过 disarm_timer**
  （只 WARN_ON_ONCE）→ 节点留在 victim 的 `pct->bases[CPUCLOCK_SCHED].tqhead`；
  真正的摘除发生在 victim 退出时的 `cleanup_timerqueue()`：
  `while((node=timerqueue_getnext(head))) { timerqueue_del(head,node); ctmr->head = NULL; }`
  ⇒ 我们的两次写在此触发，**随后还有第三写 `mem[freed+0x98] = 0`**（= HEAD_OFF 的由来）。
- **CPU 限制（重要，推翻上一轮假设）**：adb shell 落在 `apps/in_active_bg` cpuset；
  `sched_setaffinity` 到 **CPU 6/7 返回 EINVAL**（实测逐核自检）⇒ 可用集 **{0,1,2,3,4,5}**
  （3 小核 A510 + 3 大核 A710/A715）。上游调参是 exec@7(prime) + delete@2-6，**无法照搬**。
  已改为**运行时查询亲和集合**自动选核（exec=最高可用核，删除=其余，跳过 CPU0）。
  注：可用集在不同 cgroup/时刻会变（见过 0x3f / 0x5f / 0-7），所以必须运行时探测。
- **新工具：detect 模式（解耦两个未知量）**。纯 0x41 填充、不做任何伪造；因为
  `cleanup_timerqueue` 会写 `ctmr->head = NULL`，所以**只要在 recv 回来的流里出现连续 8 个零字节**
  就唯一证明「UAF 命中 + 我们成功回收」——不需要伪造指针正确。实现＝`scan_stream_zeroed()`。
- **新增/改进的 harness**（`neo9-root/cve64560/stage0.c`）：
  - 预热（占满已有 partial slab）→ 打洞（drain）→ 竞态 → **在删除核上多线程填充**（同 CPU 回收）
    → kill victim → 读回判据（stage0）/扫零（detect）→ drain
  - victim 改为 exec `sleep 30`（保持存活，使摘除时点由我们控制，必须晚于填充）
  - 参数全部 env 可调（S0_KS/S0_NDEL/S0_EXEC_CPU/S0_DEL_CPUS/S0_SOCKS/S0_MSGS/S0_SEND/S0_ATTEMPTS/S0_VERBOSE）
  - `S0_MODE=baseline|detect|affinity|stage0`
- **真机结果（截至 02:0x）**：判据通路 OK（boot_id shell 可读、解析正确、baseline 稳定）；
  但 **800+ 轮无 PASS、200 轮 detect 无 DETECT_HIT**（尺寸 192/704/1472 都试过）；
  设备全程健康。轮速 52-96ms（≈19 轮/s，远低于上游 62 轮/s）。
- **另一条被堵死的观测通道**：`/proc/sys/kernel/tainted`（WARN 会给内核打 TAINT_WARN=0x200）
  对 shell **Permission denied**；`kptr_restrict`/`dmesg_restrict`/`panic*` 同样被 vivo 挡。
  ⇒ WIN 检测只能靠 detect 模式的零写或 stage0 的读回。
- 语义上的两个待验证假设：① 竞态是否真的命中（无 oracle）；② 回收是否落在被释放的
  timer slab 页上（SLUB_MIRROR + INIT_ON_ALLOC 干扰）。detect 模式同时覆盖两者。

### 64560 编排修正（02:2x）—— exec 前提从 4% 修到 100%，但 UAF 仍零命中

- **关键 bug（已修）**：victim 的非 leader `execv`（= `de_thread` 前提）**只有 4% 轮次真的发生**

  ③ 父进程**等 ack 出现（200ms 上限）再填充**，之后才 kill、停风暴、读回。

  另有修正前 800+ 轮 forged 无 PASS。设备全程健康（多次长跑，uptime 连续）。
- **推断**：现在卡在"竞态命中率"本身。上游 0.4 wins/s @62 轮/s（≈0.65%/轮）；我们
  轮速 ≈88ms（≈11 轮/s）且在**受限 cpuset**（{0..5}：3×A510 + 3×A710，**没有 prime 核 7**）
  上跑，上游调参（exec@prime、delete@2-6）无法照搬 ⇒ 命中率可能低一个数量级以上。

### 64560 竞态机制定案（读上游修复 commit 原文，02:4x）

- **修复 commit `920f893f735e92ba3a1cd9256899a186b161928d`**（"posix-cpu-timers: Prevent UAF
  caused by non-leader exec() race"，Fixes `55e8c8e`）给出了权威交错图：
  ```
  sys_timer_delete()            exec()
    p = pid_task(pid, pid_type);  ← 读到【旧】leader
                                de_thread() → switch_leader() → release_task(old_leader)
                                  __exit_signal(old_leader):
                                    posix_cpu_timers*_exit(); unhash_task(old_leader);
                                    old_leader->sighand = NULL;   ← 在 siglock 临界区内！
    sighand = lock_task_sighand(p) ← 读到 NULL ⇒ return 0，不摘除 ⇒ free_posix_timer UAF
  ```
  ⇒ **窗口成立的条件**：删除线程读到旧 leader 之后，必须**被拖到 `sighand = NULL` 之后**
  才去读 `p->sighand`。两条路径：
  ① **siglock 自旋（主路径，窗口宽）**：`lock_task_sighand` 先读非 NULL 的 `sighand`，
     再 `raw_spin_lock_irqsave(&sighand->siglock)`；若 `__exit_signal` 正持有该锁，
     我们自旋到它释放，随后重读 `p->sighand` 已是 NULL ≠ 原值 ⇒ 解锁重来 ⇒ 返回 NULL ✓
     （`kernel/exit.c` 确认 `tsk->sighand = NULL;` 就在 `spin_unlock(&sighand->siglock);` 之前）
  ② 被调度走（CFS 时间片）-- 即上游所说"用定时器中断把窗口拉长到一个调度时间片"。
- **关键前提验证**：`transfer_pid(leader, tsk, PIDTYPE_TGID)` 在 de_thread 里
  **先于** `release_task(leader)`（用 `hlist_replace_rcu` 原地替换）⇒ **exec 完成后再删，
  `pid_task(TGID)` 解析到新 leader、sighand 有效 ⇒ 正常摘除**（这正是 v2 零命中的原因）。
  `timer_base()` 确认进程级定时器进 `tsk->signal->posix_cputimers`（组队列）✓ 与 commit
  message "enqueued in p->signal" 一致，`posix_cpu_timers_exit(old_leader)` 不会清它 ✓。
- **禁用 `__exit_signal` 顺序**：`posix_cpu_timers_exit*()` → `__unhash_process()`（detach pid）
  → **最后**才 `tsk->sighand = NULL` ⇒ 正常退出路径下 `sighand==NULL` 分支不可达
  （pid 已摘除，走 `!p`）。所以**只有非 leader exec 这条路**能造出悬空节点。
- **核配置/独占性**：1:1 的删除核分配（5 worker / 5 核）⇒ CFS 不轮转 ⇒ **永不被抢占**
  ⇒ 实测 700 轮 0 命中。改为**超订**（S0_WORKERS=15 / 5-6 核）是主要杠杆（CONFIG_PREEMPT=y ✓）。

  典型形态「内核在持锁/关中断时出错 → 机器卡住 → 21s 后 RCU stall → panic → 重启」。
  （PREEMPT_RCU 下用户态自旋属静止态，不会 stall ⇒ 不是我们用户态负载导致的 stall。）
- **崩溃的确切机制（源码级）**：我的 detect 载荷把 `expires` 置成了 **0**（零区覆盖

  `run_posix_cpu_timers() → check_process_timers() → collect_posix_cputimers()

  `ctmr->firing=1; rcu_assign_pointer(ctmr->handling,current); cpu_timer_dequeue(ctmr);`
  而 `cpu_timer_dequeue()` 是 `if (ctmr->head) timerqueue_del(ctmr->head, &ctmr->node);`
  ⇒ 读到我们填的 **`head = 0x4141414141414141`** ⇒ 解引用非法指针 ⇒ oops。
  `run_posix_cpu_timers()` 有 `lockdep_assert_irqs_disabled()` **且持 `sighand->siglock`**
  ⇒ 出错后 CPU 卡死 + 锁不释放 ⇒ 21s RCU stall ⇒ panic ⇒ 重启。**时间差完全吻合。**
- **推论（重要）**：该崩溃要求内核**真的走到那个"未摘除"的悬空节点** —— 即
  **漏洞路径已经生效**（`sighand==NULL` 或 `!p` 分支 ⇒ 不 disarm ⇒ 节点留在 tqhead）。
  而 `head` 为 0x41… 说明**我们的填充内容真的占据了那块内存 ⇒ 回收（cross-cache）成功**。
  ⚠️ 保留意见：**未回收**的悬空节点也可能崩（`SLAB_FREELIST_HARDENED` 把空闲指针放在
  `s->offset`（本 cache size=264 ⇒ offset=0x80 = `rb_right`），且 `expires`/`head` 保留旧值，
  一旦到期被 tick 处理就写飞）。所以该崩溃**更硬地证明"漏洞已触发"**，

- **结构布局（本轮钉死，与反汇编互为印证）**：
  `struct cpu_timer`：node 0x00（rb 3 指针 + expires @0x18）、**head @0x20**、pid @0x28、
  elist @0x30/0x38、firing @0x40、handling @0x48（size 0x50）；`it` 联合体在 k_itimer **0x78**
  ⇒ **k_itimer 偏移：rb 0x78/0x80/0x88、expires 0x90、head 0x98、pid 0xA0、elist 0xA8/0xB0、
  firing 0xB8、handling 0xC0**（与 `ldr x8,[x20,#0x98]` 完全一致）。
- **内核会触碰被回收 k_itimer 的三条路径**（决定载荷设计）：
  1. tick `collect_timerqueue`：**只被 `expires` 门控**（`now < expires` ⇒ 立即 return，
     不碰 firing/handling/elist/head）。⇒ **`expires` 必须很大**（本次修的地方）。
  2. `cleanup_timerqueue`（victim 整组退出）：只做 `timerqueue_del()` + `ctmr->head = NULL`，
     **不碰 pid**（本轮读源码确认，此前误以为会 put_pid）。
  3. `posix_cpu_timer_del`（id 已从 IDR 移除 ⇒ 实际不可达）：读 `pid`（`cpu_timer_task_rcu`
     与**早退路径里无条件的 `put_pid(ctmr->pid)`** ⇒ 必须 0，`put_pid` 有 NULL 保护）、
     读 `handling`（`posix_cpu_timer_wait_running` ⇒ 必须 0）。
- **`rb_erase_cached` 的 leftmost 更新（循环终止的关键）**：
  `if (root->rb_leftmost == node) root->rb_leftmost = rb_next(node);` —— 我们的载荷
  `rb_right=0` 且 `parent_color=0` ⇒ `rb_next()` 返回 NULL ⇒ `rb_leftmost=NULL` ⇒
  `timerqueue_getnext()` 返回 NULL ⇒ **`cleanup_timerqueue` 的 while 干净终止**
  （`rb_erase` 走 Case 1、`parent=NULL` ⇒ 写 `root->rb_node=NULL`；`rebalance=NULL`）。
- **修正后的安全载荷**（`build_fragment_safe()`）：0x41 底 + 每槽位
  `[0x78,0x90)` = 0（rb 三指针）、`0x90` = **UINT64_MAX**、`0x98`(head) = 0x41（保留观测点）、
  `[0xA0,0xC8)` = 0（pid/elist/firing/handling）。
- **判据两处修正**：① 单看"相位 0x98 为零"会与**我自己**的 pid=0（偏移 0xA0，错位对齐时
  落在 0xA0 相位）撞车 —— 实测 `via_zero=64/64` 全假阳性 ⇒ 改为**配对判据**
  （相位 0x90 == UINT64_MAX 且 相位 0x98 == 0）；② 新增**更强判据**：
  `RB_CLEAR_NODE` 会把节点自身内核地址写进 `__rb_parent_color`（偏移 0x78）⇒
  扫描相位 0x78/0x80 出现 `0xffff…` 指针（我们填的是 0，零假阳性）。

## 64560 回收通道：定位到两个真实缺陷（11:3x-11:5x）

### 判据安全性复核（源码）
- `cleanup_timerqueue(head)` 用的是**真实 head 参数**（不是 `ctmr->head`）：
  `while ((node = timerqueue_getnext(head))) { timerqueue_del(head, node); ctmr->head = NULL; }`
  ⇒ 检测判据（`ctmr->head = NULL` 落在 freed+0x98）成立 ✓
- `collect_timerqueue`（tick 路径）走 `cpu_timer_dequeue(ctmr)`，**读** `ctmr->head`；
  但我们的载荷 `expires=UINT64_MAX` 使得 `now < expires` 提前 return，tick 碰不到 ⇒ 安全 ✓

### ★ 缺陷 1：spray 的**分配阶数**与目标 slab 不匹配
- 实测（`/proc/slabinfo`）：`posix_timers_cache objsize=264 objperslab=31 pagesperslab=2`
  = **order-1 (8KB)**；`kmalloc-8k` 是 **order-3**（4 obj / 8 页）；全机 kmalloc 里
  **唯一 order-1 的 cache 是 `kmalloc-256`**（32 obj / 2 页）。
- **AF_UNIX socket 发送的载荷走页片段（order-0 page frag），完全不进任何 slab**
  —— 用新工具 `sprayprof` 实测：spray 7.7/15.5/28MB 后宿主机侧 slabinfo diff 里
  只有 `skbuff_head_cache`/`bio-*` 等噪声，**没有任何 kmalloc cache 增长**。
- 因此回收是**页级**的：buddy 在 free_area[0] 不足时把刚释放的 order-1 块劈成
  两个 order-0 页给我们。**一条 8KB send 正好连续填满一个 8KB 块**
  （0..4096 进第一页、4096..8192 进第二页）⇒ 块内内容 == payload[0..8192]、晶格相位恒 0。
  旧值 15840 = 3.87 页 ⇒ 一个块被消息里任意一对相邻页填充，**相位只有 1/4 概率对得上**。
- 已改 `SEND_BYTES` 15840 → **8192**（上游 ORDER1_SIZE=0x2000 同理）。

### ★ 缺陷 2：判据依赖固定相位
- 旧判据按 `0x98 / 0xA0 (mod 0x108)` 扫描，隐含"消息边界不改变相位"，只在
  SEND_BYTES 是 264 整数倍时成立。8KB 不是 ⇒ 已改为**相位无关的全流 8 字节步进扫描**：
  判据 A = 出现 `q0==~0 && q1==0`（expires 后紧跟被内核清零的 head）；
  判据 B = 出现高 16 位 0xffff 且非全 1 的 qword（`RB_CLEAR_NODE` 写入节点自身地址）。
  同时移除"SEND_BYTES 必须是 0x108 倍数"的闸门。冒烟 6 轮 0 假阳性 ✓

### 通道可行性（负面结果，重要）
- **`AF_PACKET` 从 shell 直接 EPERM**（`socket(AF_PACKET)` errno=13）——
  shell 组只有 3003(inet)，**没有 3004(net_raw)** ⇒ 标准"用户态 order-N 页分配器"
  这条路走不通。
- **`/proc/buddyinfo` 对 shell Permission denied** ⇒ 无法直接观测 buddy 阶数变化，
  只能靠 slabinfo + 行为推断。
- 新工具：`neo9-root/cve64560/sprayprof.c`（实测 spray 落进哪个 cache，宿主机侧 diff）、
  `afpacket_probe.c`（AF_PACKET order-N 通道探测，结论=不可用）。

## ★★ 64560 第三个真凶：IRQ 风暴一直是**空转**的（12:0x）

- 上游 `zt_race.c` 头部注释把机制写得明明白白：
  > "Preempt the vulnerable side with a timer interrupt at the moment it holds the
  > stale pointer, which **lengthens the window from instructions to a scheduling quantum**."
- **但我们（以及上游 fragment 里能看到的代码）只 `timerfd_settime` arm，没有任何线程
  `read()`/`poll()` 那个 fd**。timerfd 到期 → `timerfd_tmrproc` → `wake_up_locked_poll`，
  **等待队列为空时什么都不发生** ⇒ 不产生 `set_tsk_need_resched` ⇒ **不抢占**。
  ⇒ 我们此前整条 "IRQ 风暴" 路径等于空转，那个"把窗口拉长"的机制根本没生效。
- 正确实现（本轮已加，`poker_thread` + `S0_POKE`/`S0_POKE_SPIN_NS`）：
  每个**删除核**一个 timerfd + 一个**阻塞在 `read()`** 的 reader 线程；
  hrtimer 在**调用者所在 CPU**排队 ⇒ `settime` 前先 `pin(该核)`；
  到期 → 唤醒刚睡醒（vruntime 落后）的 reader → CFS 抢占正在跑的删除线程 ⇒ 窗口拉长。
  收尾要点：reader 阻塞在 read 上，必须**再给一次到期**才会返回，否则 join 会挂死
  （已在 storm 结束后 `settime(z.it_value=1µs)` 逐个唤醒再 join + close）。
- 同时把旧的空转路径默认关掉：`IRQ_FDS = 0`。
- 冒烟：5 轮，`mark=1 ack=1`，poker 干净收尾、设备无残留、uptime 连续 ✓
- 顺带量到一个硬约束：KS=5000 时 `storm_us≈3-6ms` 而 `batch_us≈10.7ms`
  ⇒ **exec 批跑在风暴窗口之外**（上游要求 batch 必须落在风暴内）。
  所以正式跑必须用大 KS（58699 时 storm≈batch≈55ms）。这条以前只在小 KS 上观察过，
  现在有了明确判据。

## 64560 竞态窗口的最终定案 + poker 效果实测（12:2x-12:4x）

- **poker 确认生效（A/B 实测）**：同一配置下
  `storm_us` = **59~70ms（POKE=0）** vs **146~182ms（POKE=1）**
  ⇒ 删除风暴被拉长 2.4~2.6×，正是"删除线程被反复抢占"的特征。
  之前的"IRQ 风暴空转"结论得到反证：修好后风暴明显变慢 ✓
- **竞态路径的源码级定案（三条）**：
  1. `kernel/signal.c: __lock_task_sighand()` 有**重读校验重试环**，注释**点名 de_thread()**：
     > "we can race with de_thread() or __exit_signal(). In the latter case the next
     > iteration must see ->sighand == NULL."
     它是 `for(;;) { sighand = rcu_dereference(tsk->sighand); if (!sighand) break;
     spin_lock_irqsave(&sighand->siglock,*flags); if (sighand == rcu_access_pointer(tsk->sighand)) break;
     spin_unlock_irqrestore(...); }`
  2. `posix_cpu_timer_del()`（UNPATCHED）两条"不 disarm"分支：
     `if (!p) goto out;` 与 `if (unlikely(sighand == NULL)) WARN_ON_ONCE(ctmr->head ||
     timerqueue_node_queued(&ctmr->node));`（注意这里**只 WARN，不 disarm**）
  3. **`kernel/exit.c: __exit_signal()`**：`bool group_dead = thread_group_leader(tsk);`
     `posix_cpu_timers_exit(tsk); if (group_dead) posix_cpu_timers_exit_group(tsk);`
     ⇒ **非 exec 的组长退出（group_dead=true）会清空组队列 ⇒ 不产生悬空节点**；
     只有 `de_thread()` 把 `leader->exit_signal = -1` 才让 group_dead=false（队列不清）。
     **⇒ 我一度推演的"免竞态确定性路径"（杀掉组长、留活线程再删 timer）被源码否掉**
     —— 那条路 group_dead=true，队列先被清空。**竞态是必需的。**
- **胜出条件的精确表述**：删除线程必须在 `pid_task()` 读到**旧 leader** 之后、读
  `p->sighand` 之前，被拖到 `__exit_signal` 把 `tsk->sighand = NULL` 之后；
  这个跨度要跨过 `transfer_pid` + `release_task` 入口 + 大半个 `__exit_signal`（数百 ns~µs），
  **不是"几条指令"**。所以抢占的**持续时间**必须足够长 —— 而我们的 `POKE_SPIN_NS` 默认 0，
  poker 醒来即阻塞 ⇒ 被抢占的删除线程几乎立刻回来，延迟覆盖不了那段跨度。
  ⇒ 正在扫 `POKE_SPIN_NS` ∈ {0, 10µs, 30µs}（每档 150 轮，KS=20000）。
- 顺带：当前可用核集 = **{0,1,2,3,4,6}**（CPU 5/7 不可用 ⇒ 又拿不到 prime 核），
  布局仍是降级的；上游为此专门有 `apply_race_cpu_limit()` + 读回校验 + `GATE_FAIL` 中止。
