## 03:40–04:20 回答"能否改 vermagic 让 ReSukiSU 适配橘子4"（+ 用户贴了 late-load 失败的日志）

**用户口径**：先问 `橘子4没有直接的内核源码，能否通过修补vermagic去让ReSukiSU适配橘子4？`，
再贴了一段真机日志（`ksud late-load` 失败）。

### 结论（结论先行）

1. **改 vermagic 可行但不够**，而且**不是首选** —— 因为 KSU 自带一条更强的通路。
2. **用户看到的那条报错与 vermagic 无关**：纯粹是 **KMI 自动探测**在厂商内核上必然失败。
3. **正解是 `ksud late-load --kmi android14-5.15`** —— `ksuinit` 会**自己改 vermagic**
   并用 `/proc/kallsyms` 把未定义符号全部重定位掉。

### 报错的确切原因（源码级）

`ksud/src/boot_patch.rs`：`Regex::new(r"(.* )?(\d+\.\d+)(\S+)?(android\d+)(.*)")`
—— 要求 `uname -r` 或 `/vendor/lib/modules/*.ko` 的 vermagic 里带 **`androidNN`** 标记。
本机 `uname -r` = `5.15.137-gc870e76526d2-dirty`（vivo 自研，无该标记），vivo 的模块也没有
⇒ `get_current_kmi()` 两条路都失败 ⇒ 源码里显式 `bail!("please specify kmi manually")`。

### ksuinit 才是"改 vermagic"的官方实现（重要发现）

`late_load/mod.rs`：KMI 被用来拼**文件名** `format!("{kmi}_kernelsu.ko")`，模块取自
**ksud 的内嵌资产**（不接受外部文件），然后
`ksuinit::load_module(&ko_data, params)` —— **用户态手工装载**，不是 `insmod`。
`ksuinit/src/lib.rs` 三步：
1. `extract_required_vermagic(kmsg)`：从内核报的 `version magic 'X' should be 'Y'` 里抠出 **Y**
2. `replace_module_vermagic(buffer, Y)`：**在内存里重建 `.modinfo`** 改成 Y（**不要求等长**）
3. `relocate_with_kallsyms`：用 `/proc/kallsyms` 重定位未定义符号，再 `init_module()`

⇒ 这条路 **vermagic 不用管、未导出符号也不再是问题**（`KALLSYMS_ALL=y`，169,722 个符号）。
剩下真正的风险：`struct module` 布局、CFI 编译器一致性、`init_module` 的 SELinux 域。

ksud 内嵌的 8 份模块（`strings assets/ksud`）：`android12-5.10` / `android13-5.10` /
`android13-5.15` / **`android14-5.15`** / `android14-6.1` / `android15-6.6` / `android16-6.12` /
`android17-6.18` ⇒ 本机对应 **`android14-5.15`**。
CLI（`ksud/src/android/cli.rs`）：`--magica [PORT]` / `--allow-shell` / `--post-magica` /
`--kmi <KMI>` / `--package-name <PKG>`。

### 内核装载器那条路的实测判据（为将来"编 137 的模块"备着）

| 门 | 实测 |
|---|---|
| vermagic | 两串**各 76 字节等长**、ko 里**只出现 1 次**（文件偏移 `0x22773`）⇒ 可原地改 |
| `MODULE_INIT_IGNORE_VERMAGIC` | **无效**：`check_modinfo()` 置 NULL 后走 `try_to_force_load()`，而 `CONFIG_MODULE_FORCE_LOAD` **两边都没开** ⇒ `-ENOEXEC` |
| MODVERSIONS CRC | ko 的 `__versions` **段大小 0** ⇒ `has_crcs=false`（整串比较）、CRC 校验不生效 |
| `struct module` 布局 | ko 的 `.gnu.linkonce.this_module` = `0x3c0`、`init_module` @ **+0x178**；决定布局的 config 开关**逐个相同**（KALLSYMS/JUMP_LABEL/TRACEPOINTS/FTRACE/KPROBES/LIVEPATCH=off/SYSFS/KASAN…），137 还多开 `MODULE_ALLOW_BTF_MISMATCH` |
| CFI/LTO | 两边都 y，但 **137 是 clang 14 / 178 是 clang 18** ⇒ 真编模块应用 **clang 14（NDK r25c）** |
| **未定义符号** | ko 依赖 215 个 **GLOBAL 且全部被重定位引用**的符号；137 的 `__ksymtab` 里**缺 52 个**（`avc_has_perm`/`avtab_*`/`ebitmap_*`/`policydb_*`/`selinux_state`/`kallsyms_lookup*`/`init_mm`/`task_work_add`/`__arm64_sys_close`…）。`resolve_symbol_wait()` 只查导出表（源码确认**无 kallsyms 兜底**）⇒ 这条路上是死穴 |

⚠️ **最后一条没定案**：用 178 的公开源码查同样的名字**也没有 EXPORT_SYMBOL**，而 ko 在 178
真机上装载成功 ⇒ 要么"vivo 公开源码 ≠ 设备导出面"，要么我枚举还有漏。**没排除前不能说
"改完 vermagic 就能装"。**

### 测量方法上的坑（记下来别再踩）

- 用 `readelf -r` 判"符号有没有被引用"时，行尾是 `+ 0`，`grep " $s$"` 会全判成 0 次 ——
  要先 `awk '{print $5}'` 取出符号列再比集合（387 个引用符号 / 215 个 UND 全在里面）。
- 枚举 `__ksymtab` 时，**只按"value_offset 落到一个 kallsyms 地址"校验会被同址别名骗出假阴性**
  （`memcpy`/`strlen`/`init_mm` 全被判"未导出"）⇒ 必须再加"name_offset 指向该地址的**别名之一**"。
- 锚点别选 `printk`（这个内核里没这个符号，`printk` 是宏，实体是 `_printk`）。
- 扫描窗口别以 `_printk` 的地址为中心 —— ksymtab 在 .rodata，与 .text 相距 35MB；要以
  **定位到的 ksymtab 条目地址**为中心（实测条目跨度只有 0.17MB = 15129 × 12B）。
- 解内核内嵌 config：`boot.img` → kernel → `IKCFG_ST…IKCFG_ED` 之间是 gzip。

### 头号结论：之前担心的"52 个未导出符号"根本不是障碍（我被实测推翻）

设备上那份 `/sdcard/kernelsu-vivo.ko` 的 md5 = **d7546a32ed485aa32ec545a3589c620d**
= 我昨天出的"只改 vermagic 的诊断副本" ✓；`/proc/modules` 里 `kernelsu 229376 1 - Live` ✓。
**原因（源码级）**：`ksud insmod` 内部就是 **`ksuinit::load_module()`**（`debug.rs:55`）——
用户态手工装载器，做两件事：
1. 把每个 UND 符号用 `/proc/kallsyms` 查到后改成 `SHN_ABS` **绝对地址**（内核不必导出它）
2. 首次 `init_module` 失败 → 读 kmsg 取出内核要求的 vermagic → 内存里替换 → 重试

⇒ **vermagic 与导出符号面都不是门槛**；`ksud late-load --kmi android14-5.15` 反而
**panic 了**（GKI 官方模块与厂商内核的 `struct module` 布局/CFI 不匹配，ksuinit 只能改
vermagic+填符号，改不了布局）⇒ 这条路判死。相关文档已按实测修正
（`neo9-root/docs/LKM_ON_OTHER_KERNEL.md` §1/§3/§5）。

8MB 块）/gzip/裸 cpio → newc cpio 里只取一个文件。

| 事实 | 值 |

### 改法：KSU 的 su 入口要"解析"，不能写死单一路径

`Terminal.kt` 新增：

```kotlin
private val KSU_SU_CANDIDATES = listOf(
    "$DEV/su_ksu",            // ① 随包（优先）
    "/system/bin/su",         // ② KernelSU 自己装的
    "/data/adb/ksu/bin/su",   // ③ 少数版本放这里
    "su",                     // ④ PATH 兜底
)
fun ksuEntry(): String?      // 依次**真执行一次 id**, 出 uid=0 即缓存并返回
fun ksuUsable(): Boolean     // = ksuEntry() != null
fun invalidateKsu()          // 入口失效时清缓存
fun ksuRun(cmd, timeoutMs)   // 用解析出的入口执行; 输出含 inaccessible/not found 时 invalidateKsu()
```

要点：**只看文件在不在不算数**（KSU 会拒绝未授权的调用者，必须真跑出 `uid=0`）；
探不到**不缓存**（KSU 可能还没加载完）；探到了缓存但失败即清。

统一替换的调用点：`HomePage`（主页 root 判定）、`Terminal.execWrapped`（终端 KSU 通道）、
`Terminal.statusLine`（显示入口名）、`Deployer` 的 `softReboot()` / `cleanupAndReboot()` /
`waitKsuSu()` / 部署流程的 `ksud insmod` ×2 / `killall` / 验证 `id` / `pm install`。
唯一保留的 `su_ksu` 字面量是「清残留」的 `rm -f` 文件名单（那不是入口）。


### 二进制核验结果（23:3x，推翻"同批 cherry-pick"推测）

- 用 vmlinux-to-elf（191887 符号）+ capstone 对 kernel.elf 反汇编核验（工具已归档
  `neo9-root/tools/verify_patches.py`，阳性对照 = 14.0.17.6 的 5.15.137 kernel.img.vmlinux）：
  - **CVE-2026-43499 remove_waiter：UNPATCHED**。197 与 137 形状逐指令一致（1×`mrs x20,sp_el0`
    → current->pi_lock(+0x10)，`x22=current+0x884` 清 current->pi_blocked_on，
    bl rt_mutex_adjust_prio_chain 以 current 收尾）。补丁版应零 sp_el0、全走 waiter->task。
  - **CVE-2026-64560 posix_cpu_timer_del：UNPATCHED**。kallsyms 无 timer_lock_sighand；
    唯一 __lock_task_sighand 调用点(0x…af8c) 后 cbz x0→0xbb138 = WARN_ON_ONCE 形状
    （ctmr->head/node-queued 检查，brk #0x800 硬陷阱）→ 直接落回 rcu 出口，无重试环。
  - **CVE-2026-64468 binder_free_transaction：UNPATCHED**。函数内无 binder_thread_dec_tmpref
    调用（无 to_thread pin）；vivo 自研 binder 钩子（binder_txn_latency_free 等）在场但
    漏洞形状完整。
- **结论**：7 月批次在 5.15.197 内核代码层面**全部存活**；"橘子6 封堵 43499"若属实，
  必是内核代码之外的层（SELinux/seccomp/框架），或封堵方式/范围需真机复核——
  内核洞还在，绕过面取决于那道"特殊手段"到底拦在哪层。
- 教训（再次）：用户情报也要过二进制核验；"构建日期晚于修复发布 ⇒ 可能同批修"的推断
  被 3/3 反例证伪。

### 21479/21385 定案：文章原理比对（23:5x）

- 用户提供 eknight-eutopia 博客《CVE-2026-21385漏洞复现》——**文章标的正是 21385**
  （修复 commit 91a0db3a，小米15/8 Elite 实测 root，完整链未公开）。原理：
  `1 << align` 下溢 + `kgsl_iommu_get_gpuaddr`（得 PAGE_SIZE）与 SVM 路径 `get_align`
  （得 SZ_2M）对齐语义分歧 + 64bit hint 分支缺校验 ⇒ 任意低 GPU 地址 ⇒ physrw ⇒ root。
  **用户所称"21479 GPU physrw 主链"与该文同源**（标签混用，两个 CVE 指向同一利用面）。
- 新旧 msm_kgsl.ko 反汇编定案（exploit 路径逐环节）：
  - OLD(14.0.17.2, g4760e0b41525)：`kgsl_iommu_get_gpuaddr` 内
    `ubfx x11,x8,#0x10,#0x10`（16 位 align！）+ `lsl w9,w9,w11`（32 位移位回绕，
    align=32 → 1）+ `cmp #1,lsl #12`/`csel` = max_t(1<<align, PAGE_SIZE)
    ⇒ **完整漏洞形状，与 14.x 真机 tier=full 自洽**。
  - NEW(16.2.13.2, g5fa6d84a8071)：三处（kgsl_get_align / get_gpuaddr /
    get_svm_unmapped_area@0xf76c）**同一钳位阈值链**（ubfx 8 位 → ≥21:2M/==20:1M/
    >15:64K/else:4K），无任何 lsl 移位 ⇒ 语义分歧消失，align 字段收窄 16→8 位。
- **结论：文档化的 physrw 利用原理在 16.2.13.2 上全部环节死亡**。physrw 主链若依赖
  此洞（大概率，与 14.x 验证链同源），16.2.13.2 需另寻入口；真机自检仍是最终裁决。
  真正的 CVE-2025-21479（micronode 授权，另一独立洞）仍无公开 diff、离线不可判定。
- 待办：fw_profile 重推计划需重新评估入口——GPU physrw 原语若依赖 alignment 分歧，
  16.2.13.2 的 P0 优先级回到 64560（posix_cpu_timer，内核侧 UNPATCHED 已证）。
