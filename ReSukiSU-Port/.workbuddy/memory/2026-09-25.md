## 追加: 内置 su (不跑 rootc + rootd)

**需求**: 做一个"内置 su"版本, 不走 rootc 配 rootd 的文件队列。参考 rootd.c (socket 服务) /
rootc.c (b64 客户端) / u0.c (setuid(0)) / client/su (su CLI)。

**实现** (exploit_vivo.c, 4227 行):
- 服务端 `stab_su_server()`: AF_UNIX `<ROOTD_DIR>/su.sock` (0666), 一次连接一条命令;
  协议 `PING` / `ID` / `EXEC <flagshex> <b64shell|-> <b64cmd>` / `SHELL <rows> <cols> [b64shell]`;
  EXEC = fork + dup2(conn,1/2) + stdin=/dev/null + `execl(shell,"sh","-c",cmd)` + 尾部 `[rc=N]`
  (完全对齐 rootd 语义); flags bit0 = 子进程先 setgid(0)/setuid(0) (u0 语义, 内置不再需要 u0 二进制)。
- SHELL = pty (`posix_openpt`+`setsid`+`TIOCSCTTY`+`sh -i`), 服务端 poll 双向转发, 客户端
  下发 winsize; pty 不可用时客户端自动退化为逐行 EXEC (与老 su 脚本一致)。
- 客户端 `stab_su_client()`: 同一二进制 `--su` (或 argv[0] 名为 su) 进入; CLI 与 client/su 对齐
  (`-c`/`CMD...` 拼接、`--u0/-0`、`-s`、`--no-path` 默认注入 PATH、`-l/-m/-p` 忽略、`--id`/`--ping`);
  流式转发 + 从响应尾部滑窗解析 `[rc=N]` 并作为退出码透传。
- 兼容: 默认再 fork 一个子进程跑原文件队列服务 (`CHEESE_SU_QUEUE=1`, 可关) → rootc 老脚本继续可用;
  同时写 `su_ready.txt` 与 `rootd_ready.txt`。
- 顺序保证: 所有 fork 都在 `stab_gpu_release()` 之后 (服务端入口还有一道"未释放则先释放"的保险)。
- 构建: `-DCHEESE_SU_DEFAULT=1` → `exploit_vivo_neo9_stable_su_ndk13/10` (脚本已加);
  包装脚本 `client/su_builtin.sh`。

**测试抓到的真 bug**: `stab_b64_dec` 的译码表把 `'='` 映射为 0 且未特判 → 非 3 倍数长度的
base64 每遇一个 padding 多吐一个字节 (长度 != 原始长度)。已修 (显式把 `=` 当结束符),
并把 `embedded_root_daemon` 里那份重复且同缺陷的解码器统一到同一个已测函数。
→ 新增 `test_su_protocol.py` (抽取真实函数编译执行, 21 组断言: b64 round-trip / rc 解析 / argv 拼接)。

## 追加: 分析 vrpatch.ko vs 文章 (Shell + libvrpatch.so) 的思路差异

结论: 名字撞了, 思路几乎相反 —— 本项目是**内核模块持久中和**, 文章是**用户态内存瞬时改写**。
关键分野与实测证据 (均来自本仓库已有文档, 未做新实验):
1. **判定模型不同**: 文章假设 vr.ko 是"行为型"检测(commit_creds/do_execve/ptrace kprobe) → 对抗手段是
   "静默钩子"; 本项目实测 vr.ko 的判定是**状态型**(`euid==0 && sid != vrp`, .text+0x2ecc 纯谓词,
   kprobe 实挂 do_init_module/avc_has_perm/module_memfree) → 最省力对抗是"不落进那个状态"
   (STUB_MODE=10/13: euid 保持 2000 + fsuid=0 + 全 caps), 根本不碰 vr.ko。
2. **作用点粒度**: vrpatch.ko 撞在**唯一收敛点**(predicate)上, 2 条指令覆盖全部检测路径;
   文章要"遍历所有检测函数偏移批量写 ret", N 个点、漏一个即失败。
3. **批量静默在本平台有实测反例**: `CHEESE_PATCH_KPROBE=1`(改全局 kprobe_dispatcher) → init 崩溃, 已禁用。
4. **无痕 vs 持久天然互斥**: 软重启不重载内核 → 内存 patch 与模块 patch 都会存活; 文章坚持完整复原
   → 换来无痕, 代价是"每次要重做 + 残留即下次读到自己的 shellcode"; vrpatch.ko 刻意不恢复
   (exit 注释明说) → 换来软重启稳定, 代价是本 boot 内 vr.ko 全线失效。
5. **前提与定位**: vrpatch.ko 前提是"已有 root/KSU"(insmod), 属于拿到 root **之后**的稳定化;
   文章前提是"已有内核内存读写原语"(漏洞), 属于**造 root 本身**。二者是上下游, 不能叠:
   文章 §7.4.4 自述禁止在 KSU 环境运行, 而 vrpatch.ko 正是 KSU 模块。
6. **文章三条前提与本机实测不符**(不改结论, 只标注): ① vr.ko "主动脱链隐藏, lsmod/proc 看不到" ——
   实测 `vr 45056 0 [permanent] Live` 在链表里可见(而 vrpatch.ko 的 find_module("vr") 正依赖这点);
   ② "自身代码段 CRC 自校验, 篡改即 panic" —— 实测直接改其 .text 且系统稳定(netd SIGABRT 26+ → 0);
   ③ "2 秒周期 task_struct 扫描" —— 确认有 kthread, 但未确认该扫描及其周期。
7. 本轮两天的工作其实已把文章"复原/校验"思想吸收到 exploit 侧 (sidecar 备份 / 信号兜底 /
   CHEESE_RESTORE_VHANGUP / CHEESE_RESTORE_ALL), 只是作用对象是 exploit 自己写的内核补丁, 不是 vr.ko。

## 追加: 真机执行驱动 (反复试到命中) + adb 接入方式

**adb 接入关键发现**: 本机 (Linux 工作机) 沙箱内 `/dev/bus/usb` 不存在 (只有 null/zero/random/tty/full/shm),
所以我自己起的 adb server 看不到设备; 而**设备其实插在这台机器上** (sysfs 可见 vivo 2d95:6013)。
正确做法: **不要在沙箱里 `adb kill-server`/`start-server`**, 直接复用用户终端已启动的 adb server
(监听 127.0.0.1:5037, 有 USB 权限) —— adb client 连上去即可看到设备。
设备: `10CE740DX90029R` (PD2338 / V2338A)。
