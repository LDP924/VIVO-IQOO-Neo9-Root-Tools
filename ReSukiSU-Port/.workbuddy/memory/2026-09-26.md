## 追加: 内置 su + u0 结合 => vr.ko 未中和也能 uid=0 (+ 装 su 到 /data/local/tmp)

用户需求: ① 内置 su 与 u0 结合, 在 vr.ko 还在的前提下实现 uid=0 显示; ② 拿到 root 后把 su 放进 /data/local/tmp。

### 机制 (理论依据来自本项目自己的文档)

VRKO_BYPASS.md §1 的检测条件是 `euid==0 && sid != u:r:vrp:s0 -> force_sig`, 即
**vrp 是白名单域**; DEBUG_RECORD.md §12.114 的谓词是
`ldr w8,[cred+0x14](euid); cbnz -> 返回; euid==0 才去比对 sid`。
=> `--u0` 只需 **先 setcon 到 vrp 再 setuid(0)**, 顺序不能反 (反了就有
"euid=0 但域非白名单"的窗口, 期间的 avc_has_perm 会命中 vr.ko 的 kprobe)。

**不需要知道 vrp 的数值 sid**: 走 /proc/self/attr/current 写入 (setcon), 内核自己做
字符串->sid 转换。实测 uid=2000 无 caps 的 shell 在 permissive 下就能 setcon 成功。
`/sys/fs/selinux/context` 是 0666 可写 (实测它只是回显, 给不出数值 sid)。

### 落地实现 (exploit_vivo.c, 纯用户态 — 没动任何 stub/偏移)

新增: `stab_u0_ctx()` / `stab_getcon()` / `stab_setcon()` / `stab_setexeccon()` /
`stab_u0_enter()` / `stab_install_su()`, 以及 3 个纯用户态子命令
(`--install-su` / `--setcon [ctx]` / `--u0test`)。
`stab_su_exec` 的 U0 分支改为调 `stab_u0_enter(cfd)`。
**硬约束"漏洞命中地址不变"天然满足** —— 一行汇编都没改。

安全闸门 (重要): `setcon` 失败就**拒绝降 uid** (返回 rc=126), 绝不进入
"euid=0 且域未知"状态。已用无效域名 `u:r:nosuchdomain:s0` 反向验证: 拒绝生效, 进程保持 uid=2000。

### 实机结果

`--u0 -c 'id'` -> `uid=0(root) gid=0(root)` + 全 caps; 连打 5 次全成;
/proc/kallsyms 可读 (caps 模式不行); /proc/vrp 仍 EPERM;
**dmesg/logcat 里 vr.ko 的 `fatal:`/`Raw_Dmp!` 痕迹 0 条** (dmesg 可读 35088 行, 负证据有效);
netd(1533)/zygote64(1534)/system_server(2349) 全程未重启, boot_id 未变。

### 未解释透的现象 (已写进 SU_BUILTIN.md §11.3, 别当结论)

exec 之后最终域**不是 vrp 而是 `u:r:kernel:s0`(sid=1)**。最小隔离:
- setcon(不 exec) -> vrp
- setcon + setgid/setuid(不 exec) -> vrp  (setuid 不改域)
- setcon + exec, uid=2000 -> vrp
- setcon + setuid(0) + exec -> **kernel**  ← 差异只由 uid=0 引起
- 加 setexeccon(放 setuid 前/后) 都压不住

已确认 `exec_sid` 在 setgid/setuid 之后会丢 (uid=2000 时 setexeccon 有效, uid=0+setuid 后无效)。
sid=1 正是 MODE13 stub 写进 `cred->security->osid` 的值 -> 怀疑 exec 在 uid=0 时从 osid 派生域, 未证实。
两种竞争解释: (a) 文档的 euid 击杀条件是纯逆向推断, MODE0/2/5 崩溃实为
`prepare_kernel_cred(0)` 的 cred 替换副作用 (被误归因); (b) 谓词会触发但本场景没走到 fatal 分支。
**定论需要**: 读回 exec 后进程的 cred->security->sid, 或用 STUB_MODE=10 (不写 osid/sid) 重新 root 对比。

### 风险边界 (写进文档)

- 不要用 `--u0` 加载内核模块 —— vr.ko 的模块触发器 (`do_init_module`/`module_memfree`)
  "不看调用者 uid", insmod 会重启设备; KSU 激活仍走 caps + vrpatch.ko 那条链。
- 其他场景优先默认 caps 模式。

## 追加: `su` 默认 uid=0 + 三个真机踩出来的坑

用户需求: "直接让设备执行 su 时直接带入 --u0 执行"。

### 实现 (全部用户态, 没动任何 stub/偏移)

1. **客户端默认 flags = STAB_SU_FLAG_U0**; 退出开关 `--caps`/`--nou0`、`CHEESE_SU_U0=0`;
   命令行优先于环境变量。
2. **`--id` 改成在子进程里套用 flags 后再报告** (新增 `stab_su_identity`), 否则报告的是
   服务端自己的 cred, 对"命令会以什么身份跑"没参考价值。
3. **协议扩展**: `ID [flagshex]`; `SHELL` 支持双格式 —— 旧 `<rows> <cols> [b64sh]`,
   新 `<flags> <rows> <cols> <b64sh|->`。客户端只在 flags!=0 时发新格式,
   这样对接旧服务端 pty 仍可用。
4. 新增诊断入口 `--su-server`: 已 root (KSU) 时不必重新命中漏洞就能起新版服务端做验证。
   **很实用 —— 本轮所有服务端改动都靠它验证。**

### 坑 1: 子进程 dup2 之后不能再用 cfd

`stab_su_exec` / `stab_su_identity` 里 `dup2(cfd,1); dup2(cfd,2); close(cfd);`
之后又把 `cfd` 传给 `stab_u0_enter()` / `stab_su_report_identity()` —— 写入全落空。
症状: `--id` 只回空 `[rc=0]`; u0 被拒绝时看不到原因。修法: 统一写 fd 1。

### 坑 2: setcon 在 Enforcing + 审计洪泛下会阻塞

`stab_u0_enter` 逐步打点定位到卡点是 `write("/proc/self/attr/current")`。对照:
- **Permissive (目标环境)**: pty+u0 一次通过, 域保持 `u:r:vrp:s0`
- **Enforcing + KSU + dmesg 洪泛**: 长时间卡住

判定为环境性而非缺陷。怀疑 `setcon` → `flush_unauthorized_files()` / denial 审计路径被拖住。
另外两条经验: (a) 持有 pty master 时做 setcon 更糟 (tty 会被 flush 处理);
(b) 诊断输出要写服务端日志而不是 pty —— 客户端 pty 模式开头会读一小段探测,
开头是 `su: ` 就误判"pty 失败"并切逐行模式 (这解释了"shell 起来了但看不到提示符")。
对策: 客户端 pty 探测加超时 (10s, `CHEESE_SU_PTY_TIMEOUT_MS`) + 明确退路提示。

### 坑 3: 服务端串行处理会被长会话堵死

su 服务端原按"一次连接一条命令"串行处理; 一个卡住的 pty 会话让它**永久卡在 relay**
(连 accept 都回不去), 后续所有 su 无响应。改成 **每连接 fork 一个子进程**
(父进程只管 accept + WNOHANG 回收), 抽出 `stab_su_handle_conn(cfd)`。

### 真机验证 (permissive, 完整矩阵)

## 追加: ReSukiSU → KSU_VERSION 35179 (源码版本对齐 + 重建 .git)

### 机制 (一切的前提)

`source/resukisu/kernel/Kbuild`:
```
LOCAL_GIT_EXISTS := $(shell test -e $(KSU_SRC)/../.git && echo 1 || echo 0)   # ==> source/resukisu/.git
```

### 重大纠正: 版本码**可以**从 ko 反查

所以定位方式: FULL 串取 sha -> git 算旧版本码 -> 搜 `mov wN, #imm16`。

## 12:15 「临时 root」通道整合 u0 → `id` 直接显示 uid=0(root)

**用户反馈**：终端「临时 root」通道执行 `id` 显示 `uid=2000(shell)`，要求"直接整合 u0 运行"。

**根因**（`exploit_vivo.c:3912-3919`，函数 `embedded_root_daemon`）：

```c
pid_t pid = fork();
if (pid == 0) {
    dup2(of, 1); dup2(of, 2); close(of);
    execl("/system/bin/sh", "sh", "-c", cmd, (char*)NULL);   // 没有 setgid/setuid
}
```

rootd 文件队列只 fork + exec `sh -c <命令>`，子进程继承 shizuku 的 uid 2000，而 SELinux
域从 exploit 继承成 kernel —— 所以一直是 `uid=2000(shell) context=u:r:kernel:s0`。
内置 su 那条路会先调 `stab_u0_enter()`（`setcon(vrp)` + `setuid(0)`），所以 su 才能 uid=0。

**为什么可以直接用 u0 提权**（关键依据）：`exploit_vivo.c:2951-2956` 的实测注释 ——
本机 euid=0 且域为 `u:r:kernel:s0`（非白名单 vrp）时**并未**被 vr.ko 击杀；部署流程里的
`u0 ksud insmod` 就是同一路径的活证据。

**改动（只在 App 侧，未改 C、未重跑漏洞）**：

- `deploy/Terminal.kt`：新增 `u0Wrap()`，投递前把命令包成
  `/data/local/tmp/u0 /system/bin/sh -c '<命令>'`（内层复用已有 `shq` 转义单引号）。
  为什么要两层引用：`u0` 的 `execv` 不做词法拆分、也不搜 PATH（两处都要绝对路径），
  而 rootd 又会用 `sh -c` 执行投递内容。

## 16:09 临时 root 的域 vrp → shell（修 Axeron/AxManager 起不来）

**用户反馈**：临时 root 下跑 Axeron（`frb.axeron.manager`）的 starter，报

**Axeron 是什么**（查证）：Shizuku 类的特权服务框架（包名 `frb.axeron.manager`，
作者 fahrez182，Apache-2.0）。它的 Root 激活路径用 libsu 起 `libaxeron.so` starter，
而 `AxeronService` 明确要求 *"waits for system services (package, activity, user, power)"*
+ *"verifies manager app installation via `getManagerApplicationInfo()`"* —— 所以拿不到
`package` 服务就直接 fatal。

**根因（avc 铁证，`permissive=0` = 真被拒）**：

```
denied { find } name=package  scontext=u:r:vrp:s0  tcontext=u:object_r:package_service:s0  tclass=service_manager
denied { list } name=service_manager  scontext=u:r:vrp:s0  tcontext=u:r:servicemanager:s0
```

`u:r:vrp:s0`（exploit 默认落脚域、vr.ko 白名单）**权限只够跑裸命令**：

| 命令 | vrp 域 |
|---|---|
| `service list` | `Found 0 services` |
| `cmd package path frb.axeron.manager` | `Can't find service: package` |

Android 的 kernel 域只给内核线程用，不含 servicemanager 权限。这解释了上一轮
`u0Wrap`（rootd/kernel 域）方案的局限：跑 `id` 没问题，但任何依赖系统服务的工具都会废。

**方案：改用 `u:r:shell:s0`**（Android 标准域，policy 对 servicemanager/package/activity

| 检查 | vrp | shell |

| `pm list packages \| grep axeron` | 失败 | **正常** |

**改动**：

| 位置 | 改动 |
